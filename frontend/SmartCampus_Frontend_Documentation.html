Common Requirements (All Frontends)

1.1 Authentication Flow

Shared across all three apps
  1. Login screen collects email + password.
  2. JWT token storage: HTTP-only cookies for web; flutter_secure_storage / react-native-keychain for mobile.
  3. Refresh token mechanism — automatic silent refresh before expiry.
  4. Logout: clear tokens, call backend logout endpoint, redirect to login.
  5. Role-based redirect after login:
       • super_admin → SuperAdmin Dashboard
       • org_admin → Organization Dashboard
       • teacher → Teacher Mobile App

1.2 API Client

ConcernWeb (Axios)Mobile (Dio)

Token injectionRequest interceptor → Authorization: BearerInterceptorsWrapper.onRequest
401 handlingResponse interceptor → refresh or logoutonError → refresh or logout

1.3 Error Handling

Global error boundary on web (React.ErrorBoundary) and error widget on mobile. All errors must show user-friendly, non-technical messages. Implement exponential back-off retry logic for network failures.

1.4 Multi-language Support (i18n)

Support minimum two languages: English + one local language. Language selector in user profile. Date/time formatting is locale-aware.

1.5 Theme Support

Light / dark mode toggle required on all platforms. Consistent color palette across apps. Responsive layout on web, adaptive on mobile.

4.6 Offline Support (Critical)

What to Cache Locally

  • Student list for each session (with photo URLs)
  • Session details (subject, time, section)
  • All pending attendance marks

Offline Attendance Sync Algorithm

Sync Flow
  1. When marking offline → store in local SQLite/Hive with key: sessionId + timestamp. Show "Saved offline" indicator in UI.
  2. App start: check for pending sync records in local DB.
  3. If online: send batch of pending attendance records to POST /api/v1/attendance/mark.
  4. On success: remove processed records from local pending store.
  5. On failure: keep records and retry with exponential back-off.
  6. Background sync via WorkManager (Android) and BGTask (iOS).

Conflict Resolution

If attendance already exists on server (e.g., marked by another teacher), newer timestamp wins. Show user a conflict dialog when discrepancy is detected.

6.3 API Client Configuration

Web — Axios

const api = axios.create({
  baseURL: process.env.NEXT_PUBLIC_API_URL,
  withCredentials: true,   // send refresh token cookie automatically
});

api.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${getAccessToken()}`;
  return config;
});

// 401 → refresh token → retry
api.interceptors.response.use(null, async (error) => {
  if (error.response?.status === 401 && !error.config._retry) {
    error.config._retry = true;
    await refreshToken();
    return api(error.config);
  }
  return Promise.reject(error);
});

Mobile — Dio (Flutter / Dart)

final dio = Dio(BaseOptions(baseUrl: env.apiUrl));

dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) {
    options.headers['Authorization'] = 'Bearer $accessToken';
    return handler.next(options);
  },
  onError: async (error, handler) {
    if (error.response?.statusCode == 401) {
      await refreshToken();
      return handler.resolve(await dio.fetch(error.requestOptions));
    }
    return handler.next(error);
  },
));

Authentication & Session Handling

7.1 Web

Web Session Strategy
  1. On login: store access token in memory (JS variable or Zustand store). Never in localStorage.
  2. Refresh token is stored in HTTP-only cookie — set by backend, never readable by JS.
  3. Use setInterval to proactively refresh the access token 1 minute before expiry.
  4. On page reload: call /auth/refresh immediately to restore session from cookie.

7.2 Mobile

Mobile Session Strategy
  1. Store access token in flutter_secure_storage (Flutter) or react-native-keychain (RN).
  2. Store refresh token in the same secure storage.
  3. Implement token refresh interceptor: on 401, call POST /auth/refresh, store new token, retry original request.
  4. If refresh also fails (expired or revoked): clear all stored tokens, redirect to login screen.

7.3 Logout Flow

  1. Clear all local tokens (memory + secure storage).
  2. Call POST /api/v1/auth/logout to invalidate refresh token on backend.
  3. Clear React Query / Bloc state cache.
  4. Redirect to login screen.
08

Offline Support (Teacher App only)

8.1 Data Cached Locally

  • Student list for each session (names, roll numbers, photo URLs)
  • Session details — subject, time, section
  • All pending attendance marks (SQLite or Hive)

8.2 Sync Algorithm

Background Sync Flow
  1. App starts → check local DB for any records with syncStatus: 'pending'.
  2. If device is online → send batch to POST /api/v1/attendance/mark.
  3. On success → mark records as 'synced', remove from pending queue.
  4. On failure → keep records, schedule retry with exponential back-off (1s → 2s → 4s → 8s…).
  5. Background sync runs via WorkManager (Android) / BGAppRefreshTask (iOS).

8.3 Conflict Resolution

If attendance for the same session/student already exists on the server (e.g., marked by admin override), newer timestamp wins. If a conflict is detected, show the teacher a non-blocking dialog explaining the discrepancy and the final resolved value.

Next Steps

Implementation Order
  1. Choose frameworks — Next.js for both web apps, Flutter for mobile.
  2. Set up monorepo (Turborepo) for web or two separate Next.js projects.
  3. Implement the backend first (or in parallel) — all API endpoints as documented.
  4. Create shared API client package with OpenAPI / Swagger generator for typed requests.
  5. Build the shared UI component library (packages/ui) for web — ensures consistency.
  6. Develop each frontend incrementally: Auth → Core features → Analytics → Reports.
  7. Set up CI/CD with GitHub Actions for all three apps before writing feature code.
